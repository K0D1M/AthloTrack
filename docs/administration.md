# Administration

Most of these tasks can now be done in the app's admin dashboard («Διαχείριση», see [below](#admin-dashboard)). The steps in the Supabase dashboard and SQL Editor still work as a fallback.

All of the fallback steps are done in the Supabase dashboard of the project. No email provider is configured, so Supabase can't send confirmation or password-recovery emails. The steps below avoid email completely.

## Admin dashboard

An administrator is a third kind of login, next to coaches and athletes. It signs in on the normal login screen, with either the coach or the athlete form, and sees only the dashboard:

| Tab | Shows | Can do |
|---|---|---|
| **Επισκόπηση** | Counts: coaches, athletes and how many have a login, active users (7 and 30 days), users with the app, workouts this week / month, completion and read rate over 30 days, measurements this month. **Έλεγχοι** (health checks) and the latest activity across all coaches. **Ιστορικό ενεργειών**: every admin action. | Open a check to see its list |
| **Προπονητές** | Every coach: athletes, last sign-in, whether they still use the temporary password, whether they have the app | **+** creates a coach (login and profile) and shows a temporary password once. Νέος προσωρινός κωδικός. Επιβολή αλλαγής κωδικού. Διαγραφή (type the email to confirm; deletes their athletes too) |
| **Αθλητές** | Every athlete, filtered by coach, by whether they have a login, and by search | Μεταφορά σε άλλον προπονητή. Νέος προσωρινός κωδικός. Διαγραφή (type the name to confirm; the login stays) |
| **Ειδοποιήσεις** | Every device with the app (Android, and browsers that allowed notifications) | Δοκιμή: a test push to that user. **Ανακοίνωση**: a push to everyone, all coaches or all athletes |

The health checks:
- logins with no profile;
- athletes with no email;
- athletes with an email but no login yet;
- athletes with no new measurement or workout for 30 days;
- coaches still on the temporary password after 7 days;
- devices of logins with no profile.

Temporary passwords are generated by the server, shown once, and never stored by the app. Coaches must choose their own at their next sign-in.

### How it's secured
The app only has the public (anon) key.
- **Reads and simple changes:** the `admin_*` database functions (`supabase/011_admin.sql`). Each one first checks `is_admin()`, so anyone else gets an error.
- **Logins and pushes:** the Edge Function `admin` handles creating a login, setting a password, deleting a login, and sending pushes. It checks the caller's token against `admins` on every request, and only it uses the service-role key.
- **Audit:** every action is written to `admin_audit`.

### Setting it up (once)
1. **SQL Editor:** run `supabase/011_admin.sql`.
2. **Make yourself admin.** Create your login in **Authentication → Users → Add user** (Auto Confirm), then run:
   ```sql
   insert into admins (auth_user_id, full_name, email)
   select id, 'Ονοματεπώνυμο', email from auth.users where email = 'you@mail.com';
   ```
   Use a separate email from any coach or athlete account. A login that is also a coach signs in as the coach.
3. **Edge Functions → Deploy a new function** named `admin`, with the contents of `supabase/functions/admin/index.ts`. It needs no secrets of its own.
4. **Re-deploy `push`** with the current `supabase/functions/push/index.ts`. It now also accepts the admin's test pushes and announcements.

To remove an admin: `delete from admins where email = 'you@mail.com';`

## Auth settings

- **Authentication → Sign In / Providers → Email → Confirm email: off.** New athlete accounts can then sign in straight away, without a confirmation email.
- Don't use the dashboard's "Send password recovery" button. Its link points to the Site URL (by default `http://localhost:3000`), and the app has no recovery page. To reset a password, follow [Resetting a password](#resetting-a-password) below.

## Creating a coach

Coaches don't sign themselves up. An administrator creates their account:

1. **Authentication → Users → Add user → Create new user.** Enter the coach's email and a temporary password, and tick *Auto Confirm User*.
2. **SQL Editor**, then run:
   ```sql
   insert into coaches (auth_user_id, full_name, email)
   select id, 'Ονοματεπώνυμο', email from auth.users where email = 'coach@mail.com';
   ```
3. Send the coach the email and the temporary password. Because `must_set_password` defaults to `true`, the app asks them to choose their own password the first time they sign in.

To make a coach choose a new password again at their next sign-in, run:
```sql
update coaches set must_set_password = true where email = 'coach@mail.com';
```

## Linking athletes to their accounts

Linking works by email and happens automatically, whichever step comes first:

- **The coach adds the athlete first** (with an email), and **the athlete signs up later** with the same email. On signup, trigger `link_athlete_on_signup` links the account to the profile.
- **The athlete signs up first**, and **the coach adds the athlete or sets their email later**. Trigger `link_athlete_on_email` finds the existing login and links it.

Emails are compared case-insensitively. Each login links to at most one athlete, and each athlete email must be unique.

A login without a matching athlete profile can sign in but has nothing to see until the coach adds them.

To check which athletes have a linked account:
```sql
select full_name, email, auth_user_id is not null as linked from athletes order by full_name;
```

## Resetting a password

Run this in the **SQL Editor**, with the new password and the user's email:
```sql
update auth.users
set encrypted_password = crypt('NewPassword123', gen_salt('bf'))
where email = 'user@mail.com';
```
For a coach, also run the `must_set_password = true` update above, so they replace the temporary password with their own.

## Removing people

- **Delete an athlete** (from the app, or with `delete from athletes where …`). Their measurements, workouts and notifications are deleted with them. Their login stays in **Authentication → Users**, where you can delete it too.
- **Delete a login** in **Authentication → Users**. Its coach or athlete row is deleted along with it (`on delete cascade`). Deleting a coach's login removes all of that coach's athletes.

## Testing

The live project has two permanent test accounts: `coach.test@example.com` (a coach) and `athlotrack.selftest@example.com` (an athlete of that coach). Keep them. For anything destructive, create throwaway accounts instead, never use real ones, and delete them afterwards:
1. Create a test coach as in [Creating a coach](#creating-a-coach) (e.g. `coach.test@example.com`), and a test athlete under it with a throwaway email.
2. When you're done:
   ```sql
   delete from auth.users where email in ('coach.test@example.com', '<test athlete email>');
   ```
   This also removes the test coach's profile, athletes, workouts, notifications and push tokens (cascade).

The integration tests in `AthloTrack.Tests` use such accounts through environment variables; see [architecture.md](architecture.md#tests).
